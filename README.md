# WER v22.2-UDP

> **Твоя безопасность — в твоих руках.**

WER (Wide Encrypted Relay) — самописный протокол защищённой передачи файлов на C#
(.NET 8) с нуля: без сторонних криптобиблиотек и без HTTP/HTTPS. Гибидная схема
RSA-3072 + AES-256-GCM поверх **собственного надёжного транспорта по UDP**.

## Возможности

- **Свой транспорт поверх UDP.** Сессии по `(endpoint, sessionId)`, 3-way SYN/SYNACK/ACK,
  SEQ/ACK, скользящее окно 256 КиБ, буфер переупорядочивания, адаптивный RTO,
  ретрансмиссия и явное закрытие FIN/RST. Нет head-of-line blocking, присущего TCP.
- **Гибридное шифрование.** Аутентификация по RSA-3072 (подпись challenge, RSA-PSS),
  передача premaster-секрета через RSA-OAEP, вывод ключей HKDF-SHA256, шифрование
  трафика AES-256-GCM. Каждый фрейм имеет свой nonce и тег аутентификации.
- **Защита от MITM.** Модель TOFU: отпечаток ключа сервера сохраняется в
  `~/.wer/known_servers`; строгая проверка через `--pin`.
- **Докачка.** Незавершённый файл остаётся как `.wer-<id>.part`; повторный запуск
  `wer-client send` продолжит с сохранённого смещения.
- **Контроль целостности.** SHA-256 файла считается до передачи и сверяется после.
- **Пароли на ключи.** `WER_KEY_PASSWORD` шифрует приватные ключи на диске (PKCS#8 + PBES2).

## Требования

- .NET 8 SDK (или .NET 8 Runtime для готовых сборок)
- Windows / Linux / macOS
- Открытый **UDP**-порт на сервере и его проброс, если сервер за NAT

## Сборка

```bash
dotnet build WER.sln -c Release
```

Готовые бинарники (два отдельных exe):

```bash
dotnet publish src/Wer.Server -c Release -o dist/server
dotnet publish src/Wer.Client -c Release -o dist/client
```

Результат: `dist/server/wer-server.exe` и `dist/client/wer-client.exe`
(на Linux/macOS — исполняемые файлы без расширения).

## Использование

### 1. Запуск сервера

```bash
wer-server --port 9021 --data ./wer-data --reg-token SECRET
```

| Опция | По умолчанию | Назначение |
|---|---|---|
| `--port` | `9021` | UDP-порт прослушивания |
| `--max-conn` | `100` | Лимит одновременных сессий |
| `--max-per-ip` | `16` | Лимит сессий с одного IP |
| `--data` | `./wer-data` | Каталог для ключей, пользователей и принятых файлов |
| `--reg-token` | — | Токен регистрации новых пользователей |
| `--max-file-size` | 4 ГиБ | Максимальный размер файла в байтах |
| `--max-users` | `10000` | Лимит зарегистрированных пользователей |
| `--open-registration` | выкл. | Разрешить регистрацию без токена (только для локальных тестов) |

**Регистрация по умолчанию отключена.** Чтобы заводить новых пользователей, задайте
`--reg-token SECRET` (или `WER_REGISTER_TOKEN`). Флаг `--open-registration` открывает
регистрацию без токена и пишет предупреждение в лог — не используйте его на публичном сервере.

### 2. Регистрация пользователя

```bash
wer-client register 127.0.0.1 9021 alice --token SECRET
```

Создаёт пару ключей `~/.wer/wer_alice.key.pem`. При первом подключении клиент
показывает отпечаток ключа сервера и сохраняет его в `~/.wer/known_servers` (TOFU).

### 3. Отправка файла

```bash
wer-client send 127.0.0.1 9021 alice "C:\path\to\file.bin"
```

Файл окажется в `wer-data/received/alice/`. При обрыве — повторите ту же команду,
передача продолжится. Для строгой проверки сервера добавьте `--pin SHA256_HEX`.

Переменные окружения: `WER_KEY_PASSWORD` (пароль приватных ключей),
`WER_REGISTER_TOKEN` (аналог `--token` / `--reg-token`).

Коды возврата: `0` — успех, `1` — аргументы, `2` — протокол, `3` — таймаут,
`4` — сеть, `5` — файлы, `6` — состояние, `130` — прервано.

## Безопасность

Протокол **не проходил независимый криптографический аудит** и не является заменой
TLS. RSA-OAEP переносит premaster напрямую, поэтому forward secrecy нет. Для передачи
через недоверенные сети (Интернет) предпочтительнее TLS 1.3 или SSH-туннель.
Приватные ключи и `*.part` не коммитьте — они в `.gitignore`.

UDP-транспорт требует открытого UDP-порта: часть файрволов и NAT режет такие сессии,
поэтому проверяйте связность до начала передачи больших файлов.

### Что исправлено в v22.2

Формат пакета изменён (версия заголовка 2), клиент и сервер обновляются вместе.

- **HMAC-8 на каждом пакете после handshake.** Формат `[заголовок 18][HMAC-8][payload]`,
  флаг `AUTH` в заголовке, ключ выводится из сессионного через HKDF. Подделанные RST,
  ACK и window от посторонних отбрасываются — проверено MITM-релеем, который видит
  счётчики и бьёт в обе стороны каждые 200 мс: передача проходит, SHA-256 сходится.
- **Переходное окно закрыто.** Пакет с `AUTH`, пришедший до появления ключа
  (например, `Finished`), откладывается и разбирается после его установки — иначе
  8 байт тега уезжали в поток как данные.
- **RST до аутентификации игнорируется**: посторонний больше не может «ветировать»
  handshake или соединение поддельным сбросом.
- **ACK за пределы отправленного и устаревшие ACK отбрасываются**, а не зажимаются —
  поддельный счётчик больше не выбрасывает неподтверждённые данные.
- **Handshake под лимитом**: 60 попыток в минуту на IP (burst 10), таймаут 5 с.
- **Resume не перечитывает `.part`**: состояние SHA-256 кэшируется в памяти по пути
  файла; `FILE_META` ограничен 10 в минуту на пользователя.
- **Потерянный ACK на SYNACK не убивает сессию**: клиент повторяет его, пока не
  придёт любой ответ сервера.

### Что исправлено в v22.1

- **Флуд SYN больше не создаёт состояние.** Серверный ISN выводится из
  `HMAC(endpoint, sessionId, clientIsn)` (SYN-cookie), а объект сессии, поток
  ретрансмиссии и запись в таблицу появляются только после корректного ACK.
  На SYN отвечает не более 300 пакетов в секунду с одного IP.
- **Логи не забивают диск.** Повторяющиеся отклонения соединений и ошибки протокола
  пишутся не чаще раза в 5–10 секунд, с числом подавленных повторов.
- **Перечисление пользователей закрыто.** Для незарегистрированного имени сервер
  отдаёт обычный `CHALLENGE` (по приманочному ключу RSA-3072) и падает только на
  неверной подписи — отличить существующего пользователя от несуществующего нельзя.
- **Регистрация закрыта по умолчанию** (см. `--reg-token` / `--open-registration`).
- **Очереди приёма ограничены:** собеседник, игнорирующий объявленное окно, роняет
  свою сессию, а не память сервера.
- **ACK за пределы отправленного игнорируется**, RST принимается только со счётчиком,
  который виден участнику сессии.

### Известные ограничения

- Handshake идёт без HMAC (ключа ещё нет): участник канала может сбросить его, подделав
  RST, но не может «ветировать» соединение — такой RST игнорируется до таймаута.
- Высокий поток пакетов (десятки тысяч в секунду) нагружает единственную петлю
  приёма примерно на ядро, даже если все они отбрасываются.
- Кэш состояний SHA-256 живёт в памяти процесса: resume после перезапуска сервера
  снова перечитывает `.part`.
- Квот на объём принятых файлов и срока жизни `.part` нет.
- `register` отвечает `Пользователь уже существует`, что раскрывает имя при наличии
  токена регистрации.
